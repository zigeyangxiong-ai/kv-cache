## E1 一个副本突然宕机

**相关保证：** 写入只要 1 个副本确认（W=1）；另一个副本还在时仍能读到

**实验前预测：** 先确认 key 在两个副本上都存好，再停掉首选节点。入口读取会先问首选节点失败，转去问备份节点，仍然读到原值；之后的新写入只有备份节点能确认，W=1 所以仍然返回成功。

**操作与返回：**

1. `写入 e1-0=v1（首选节点 0，备份节点 1） -> {"ok": true, "version": 1, "acks": [0, 1], "replicas": [0, 1]}`
2. `直接查节点 0 -> {"ok": true, "found": true, "value": "v1", "version": 1}`
3. `直接查节点 1 -> {"ok": true, "found": true, "value": "v1", "version": 1}`
4. 停掉节点 0（kill 进程）
5. `通过入口读 e1-0 -> {"ok": true, "found": true, "value": "v1", "version": 1, "from_node": 1}`
6. `通过入口写 e1-0=v2 -> {"ok": true, "version": 2, "acks": [1], "replicas": [0, 1]}`
7. `再读 e1-0 -> {"ok": true, "found": true, "value": "v2", "version": 2, "from_node": 1}`

**实际结果：**

- 停节点前两个副本都有数据：True
- 停节点后读到 value=v1，来自节点 1
- 停节点后写入 ok=True，确认的节点 acks=[1]

**对照：** 符合预测

**解释：** 读取在首选节点连不上时自动换到备份节点；写入只得到 1 个确认也算成功，这正是 W=1 的含义。代价是：此刻这条新数据只有 1 份，如果节点 1 也挂掉，v2 就丢了。

## E1b 写入成功后唯一存好的节点也宕机

**相关保证：** W=1 不保证两份都存好

**实验前预测：** 先停掉备份节点，再写入：只有首选节点确认，入口仍返回成功。然后停掉首选节点，再启动备份节点。备份节点上没有这条数据，首选节点又连不上，入口应返回 NODES_UNAVAILABLE，而不是“未找到”。

**操作与返回：**

1. 先停掉备份节点 1
2. `写入 e1b-4 -> {"ok": true, "version": 1, "acks": [0], "replicas": [0, 1]}`
3. 再停掉首选节点 0
4. 重新启动节点 1（内存是空的）
5. `通过入口读 e1b-4 -> {"ok": false, "error": "NODES_UNAVAILABLE", "unreachable": [0], "replicas": [0, 1]}`

**实际结果：**

- 写入时 ok=True，acks=[0]（只有 1 个节点确认）
- 之后读取返回 ok=False，error=NODES_UNAVAILABLE，连不上的节点 [0]

**对照：** 符合预测

**解释：** 客户端曾经收到“写入成功”，但数据只存在于已宕机的节点 0 上。这就是“写入成功究竟表示几个节点保存了”的答案：W=1 时只保证至少 1 个。入口没有说“不存在”，因为节点 0 只是暂时连不上，无法判断。

## E2 同一条内部写入消息重复发送 3 次

**相关保证：** 版本号相同的重复消息不改变值，也不延长过期时间

**实验前预测：** 第 1 次被保存（applied=true），第 2、3 次被识别为重复（applied=false），值和到期时间都保持第 1 次的。

**操作与返回：**

1. `第 1 次发送 version=7 到节点 0 -> {"ok": true, "stored_version": 7, "applied": true}`
2. `第 2 次发送 version=7 到节点 0 -> {"ok": true, "stored_version": 7, "applied": false}`
3. `第 3 次发送 version=7 到节点 0 -> {"ok": true, "stored_version": 7, "applied": false}`
4. `等 2.3 秒后查节点 0 -> {"ok": true, "found": false}`

**实际结果：**

- 三次 applied 分别为 [True, False, False]
- 2.3 秒后 found=False（按第 1 次的 2 秒过期）；节点统计 ignored_old=2

**对照：** 符合预测

**解释：** 节点比较版本号，相同版本直接忽略，所以重复消息是幂等的。注意：这里重复的是同一条内部消息；如果客户端把 /set 请求本身重发 3 次，入口会分配 3 个不同的版本号，那是 3 次独立写入。

## E3 消息延迟 10 秒后乱序到达

**相关保证：** 节点上版本号只增不减，旧消息不会覆盖新值

**实验前预测：** 先把 version=2 的新值写到节点，再让 version=1 的旧值延迟 10 秒后到达。开启版本比较时，旧值被忽略；作为对照，关掉版本比较时，旧值会把新值覆盖掉。

**操作与返回：**

1. `[开启版本比较] 先到达：version=2 value=NEW -> {"ok": true, "stored_version": 2, "applied": true}`
2. [开启版本比较] 旧消息在路上延迟 10 秒……
3. `[开启版本比较] 后到达：version=1 value=OLD -> {"ok": true, "stored_version": 2, "applied": false}`
4. `[开启版本比较] 查节点 0 -> {"ok": true, "found": true, "value": "NEW", "version": 2}`
5. `[关闭版本比较（对照组）] 先到达：version=2 value=NEW -> {"ok": true, "stored_version": 2, "applied": true}`
6. [关闭版本比较（对照组）] 旧消息在路上延迟 10 秒……
7. `[关闭版本比较（对照组）] 后到达：version=1 value=OLD -> {"ok": true, "stored_version": 1, "applied": true}`
8. `[关闭版本比较（对照组）] 查节点 0 -> {"ok": true, "found": true, "value": "OLD", "version": 1}`

**实际结果：**

- 开启版本比较：最终值 = NEW
- 关闭版本比较：最终值 = OLD

**对照：** 符合预测

**解释：** “这行版本比较代码删掉会怎样？”——旧消息晚到时会把新值盖掉（对照组读到 OLD）。版本号由入口统一分配，不依赖各台机器的物理时钟，所以时钟不准也不影响这个比较。

## E4 节点重启后丢失内存状态

**相关保证：** 缓存允许单个节点丢数据；另一份副本仍可读

**实验前预测：** 重启首选节点后，它自己查不到这个 key；通过入口读取，首选节点回答“没有”，入口再问备份节点，仍能读到。重启的节点不会自动从别的节点补回数据。

**操作与返回：**

1. `写入 e4-1 -> {"ok": true, "version": 1, "acks": [0, 1], "replicas": [0, 1]}`
2. 重启节点 0
3. `直接查节点 0 -> {"ok": true, "found": false}`
4. `通过入口读 -> {"ok": true, "found": true, "value": "keep-me", "version": 1, "from_node": 1}`
5. `读完后再直接查节点 0 -> {"ok": true, "found": false}`

**实际结果：**

- 节点 0 重启后 found=False
- 入口读到 value=keep-me，来自节点 1
- 入口读完后节点 0 仍然 found=False（没有自动补齐）

**对照：** 符合预测

**解释：** 数据只放在内存，进程重启就清空，这是我们为了简单做的取舍。入口仍能从备份节点读到。但此时这个 key 只剩 1 份，第一版没有做“读修复”或后台同步，报告里要说明这是已知限制。

## E5 某个 key 占据 50% 的读请求（热点）

**相关保证：** 按 key 取模分片时，热点 key 会集中到它的首选节点

**实验前预测：** 均匀访问时 3 个节点收到的读请求大致相同；让 50% 的读集中到一个 key 后，这个 key 的首选节点会明显更忙，大约多承担 50% 的总读量。

**操作与返回：**

1. 预先写入 300 个 key；热点 key = user:0，它的首选节点是 0
2. 均匀访问：发 3000 次读，各节点收到 [1046, 1011, 943]
3. 50% 打到热点：发 3000 次读，各节点收到 [1990, 542, 468]

**实际结果：**

- 均匀访问：节点 0/1/2 = 1046/1011/943，平均延迟 22.17 ms，P95 38.38 ms
- 热点访问：节点 0/1/2 = 1990/542/468，平均延迟 22.64 ms，P95 41.31 ms
- 节点 0 承担的读请求占比：35% → 66%

**对照：** 符合预测

**解释：** 读取总是先问首选节点，所以热点 key 的读请求全部落在同一个节点上，取模分片无法分散单个 key 的压力。延迟在本机上差别不大，因为三个进程共用一台电脑，没有真正的网络和 CPU 瓶颈。可能的改进（第一版没有做）：热点 key 的读请求随机分给两个副本，或在入口加本地缓存。

## E6 TTL 到期失效

**相关保证：** 带 TTL 的数据到期后读不到

**实验前预测：** 写入 TTL=2 秒的数据，1 秒时能读到，2.5 秒时读不到（返回 found=false，而不是错误）。

**操作与返回：**

1. `写入 e6-4，ttl_seconds=2 -> {"ok": true, "version": 1, "acks": [1, 2], "replicas": [1, 2]}`
2. `1 秒后读 -> {"ok": true, "found": true, "value": "short-lived", "version": 1, "from_node": 1}`
3. `2.5 秒后读 -> {"ok": true, "found": false, "replicas": [1, 2]}`

**实际结果：**

- 1 秒时 found=True；2.5 秒时 found=False，ok=True

**对照：** 符合预测

**解释：** 节点在读取时检查到期时间，过期就删掉并当作不存在（惰性删除）。

## E7 LRU 淘汰最久没用的数据

**相关保证：** 节点条目数超过容量时，淘汰最久没被读写的那条

**实验前预测：** 把节点容量设为 3。写入 A、B、C 后读一次 A，再写 D：B 是最久没被用过的，应被淘汰；A、C、D 保留。

**操作与返回：**

1. `写入 A -> {"ok": true, "stored_version": 1, "applied": true}`
2. `写入 B -> {"ok": true, "stored_version": 1, "applied": true}`
3. `写入 C -> {"ok": true, "stored_version": 1, "applied": true}`
4. `读一次 A -> {"ok": true, "found": true, "value": "A", "version": 1}`
5. `写入 D -> {"ok": true, "stored_version": 1, "applied": true}`

**实际结果：**

- 各 key 是否还在：{'A': True, 'B': False, 'C': True, 'D': True}
- 节点统计：size=3，evicted=1

**对照：** 符合预测

**解释：** 节点用 OrderedDict 记录访问顺序，每次读写都把 key 移到末尾，满了就删掉最前面那条。

## E8 系统时间突然倒退一分钟

**相关保证：** 版本比较不依赖物理时钟；但 TTL 依赖物理时钟

**实验前预测：** 把节点时钟调慢 60 秒：(1) 版本比较照常工作，旧版本仍被拒绝；(2) 一条已经过期的数据会“复活”，又能读到。第 (2) 点是我们设计的已知限制。

**操作与返回：**

1. `写入 version=2，1 秒后到期 -> {"ok": true, "stored_version": 2, "applied": true}`
2. `把节点 0 的时钟调慢 60 秒 -> {"ok": true, "clock_offset": -60.0}`
3. `时钟倒退后，发来 version=1 的旧消息 -> {"ok": true, "stored_version": 2, "applied": false}`
4. `等 1.5 秒（按真实时间已过期）后查节点 0 -> {"ok": true, "found": true, "value": "v2", "version": 2}`

**实际结果：**

- 旧版本是否被写入：applied=False
- 真实时间已过期，但节点时钟慢了 60 秒，读取 found=True，value=v2

**对照：** 符合预测

**解释：** “为什么不能只用物理时钟解决冲突？”——如果用时间戳比较新旧，时钟倒退后新写入会被当成旧数据。我们用入口分配的版本号，所以 (1) 不受影响。但 TTL 用的是物理时间，时钟倒退会让过期数据多活一会儿；对缓存来说可以接受，但报告里要承认。
